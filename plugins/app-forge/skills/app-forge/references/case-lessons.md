# 作成事例から持ち出せる設計判断

以下は作者の作業記録・構成を確認して抽象化したもの。本体のコピーや、ストア審査実績の紹介ではない。

## KIRU型：ブラウザで動画を扱う

軽いプレビューと重い書き出しを切り分ける。音声・字幕・映像の時刻を同じモデルで扱い、カットを戻したときにも同期が保たれるようにする。ファイル全体を文字列にしてブラウザ自動操作へ渡すと大容量で破綻しやすい。長い素材、保存容量、GPUの状態まで実データで測る。

最初の一歩は短い素材の読込→範囲選択→再生→書き出し。検証は「短い素材が1回出た」から「長い素材でも最後まで出る」へ広げる。素材・効果音・書体の利用権と再配布権は別に管理する。

## MIRU型：動画に指摘を付けて共有する

動画・版・指摘・利用者・権限を別データにする。招待した人の役割をサーバーで判定し、管理画面の持ち主にも他人の非公開データを自動開放しない。大きいデータは同じファイルの再転送を避け、使用量と上限を実測して見せる。

最初の一歩は動画を再生→時刻に指摘→再度開いて同じ時刻へ移動。外部ストレージを入れる前に、この往復を小さなサンプルで作る。OAuthはその製品専用の設定・同意画面で確認する。

## X Sheet Clip型：Chrome拡張から外部へ保存する

通常の閲覧や「いいね」に暗黙の送信を混ぜず、専用ボタンと確認画面で意図を明確にする。URLを正規化して重複登録を防ぎ、外部の表で既存の書式を壊さない。拡張のコードに書いた値は利用者から読めるため、共通の秘密として使わない。

最初は拡張のローカル保存で往復を完成させる。外部シートは別のアダプターとして足し、送信中断・認証切れ・再送による重複を試す。作者の実際のシートURLや鍵を初期値にしない。
