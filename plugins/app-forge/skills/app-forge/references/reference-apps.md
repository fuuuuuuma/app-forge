# 参考アプリから独自のアプリへ

参考のURL・スクリーンショット・操作動画を、利用可能なブラウザや画像読み取りで観察する。サインインが要る画面は利用者が見せた資料か許可されたアカウントの範囲で読む。取得できない部分は推測と区別する。

`REFERENCE_NOTES.md` に、画面名／ユーザーの目的／入力／操作／結果／読み込み・空・エラー／戻る先を記録する。見た目だけでなく、例えば「語彙を保存→復習→会話で使う」という行動の循環を取り出す。優先する画面は最初の操作と最も価値が出る画面。

参考の観察と、自作で採用する仕様を別々に書く。配置のリズム・操作のわかりやすさ・情報の優先順位などを学び、独自の名前・文章・素材・データで実装する。許諾不明のロゴや画像、非公開の実装や利用者データを配布しない。ユーザーが自分のコードや素材を提供した場合は、その利用範囲を尊重する。

画面の一致が目的なら、対象となる画面と幅、フォント、余白、色、並びを計測し、実装後に同じ条件で比較する。動作の一致が目的なら、同じ入力と操作で期待した状態になることを検証する。参考サービスの利用規約やアクセス制限を回避して情報を取らない。

最初の指示例：

> この参考アプリの「記録して振り返る」流れを使って、撮影メモのWebアプリを作って。最初はメモ登録・検索・週ごとの振り返り。素材と名前は自分のものにして、スマホ幅で使えるところまで実装して。

## 抽象的なアイデアを最初の指示へ

最初の指示では、作りたい機能に加えて、どんな画面で使うか、読込中の見せ方、データの保存先、ログインの要否、AIに任せる部分、完成を確かめる操作を具体化すると実装の範囲が伝わる。未定の項目は採用理由を示して仮置きする。装飾・認証・外部AIをすべてのアプリに加える必要はない。

この整理は[THE FIRST PROMPTの動画](https://x.com/usutaku_channel/status/2111464216599429238)の字幕表示を複数フレームで観察した着想。動画に出る特定のデザインやサービスの採用は、利用者の目的と環境で決める。公開や課金までを初回の曖昧な指示から許可済みとみなさない。
