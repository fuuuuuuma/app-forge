# 伝わるUIと、確かめる動作

用語は必要な体験を指定するために使う。全部のUI部品を入れるための一覧にはしない。

| 指示語 | 使う場面 | 確かめること |
| --- | --- | --- |
| Pull to Refresh | 一覧を引っ張って最新を取得 | スクロールと衝突しない、二重取得しない、失敗を伝える |
| Skeleton Screen | 読み込み後の形を先に見せる | レイアウトが急に飛ばない、読めないダミーを本物として読ませない |
| Toast | 保存など短い結果を伝える | 画面読み上げでも分かる、重要な失敗は消える通知だけにしない |
| Bottom Sheet | 現在の画面を残して詳細や操作を出す | 閉じる・戻る・フォーカス移動・キーボード表示 |
| Swipe Action | 一覧の行から操作する | スワイプできなくてもボタンで操作可能、削除の取り消し |
| Autocomplete | 入力候補で入力を減らす | 日本語変換の途中を壊さない、候補なし、キーボードで選べる |

この6用語の着想は[うすたく氏の投稿](https://x.com/usutaku_channel/status/2112106482493772057)。説明と検証観点は本配布物で独自に整理。

## 一連の操作で確認する

たとえば記録アプリなら、新規入力→保存→再表示→再読込→編集→検索→削除/復元を通す。年月日・時刻・通貨が関わるときはタイムゾーンと境界を試す。共有アプリは別アカウントと権限を試す。大容量ファイルを扱うときは実サイズで転送中断と再開を試す。

幅を狭めた状態で本文・入力欄・モーダル・長いURLが横にはみ出さないこと、キーボードだけで主操作ができることを確認する。モバイルではタッチ領域・セーフエリア・仮想キーボードと入力欄の重なりも確認する。動きを減らす設定を尊重する。

空・読込中・失敗・権限なし・オフラインのうち該当する状態を用意する。画面にないダミーAPIを本番動作として見せない。実ブラウザ/端末で確認できなければ、何を確認できていないか残す。

## 実際に読み込む入口で検証する

関数の試験が通っていても、配信されたHTMLが別のスクリプトを参照していれば画面は動かない。利用者が開くURLから読み込み、初期化完了の表示と最初のボタン操作を確認する。HTMLのscript指定・moduleの読込先・配信MIME・起動コマンドを同じ経路で揃える。環境制限のために別の起動構成を足す場合も、その入口を未検証のまま既定にしない。
