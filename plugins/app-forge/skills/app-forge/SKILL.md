# アプリ開発のすゝめ / App Forge

利用者の困りごとを、手元で実際に動かせるアプリへ変える。企画だけで終わらず、実装・起動・主要操作の確認まで進める。既存リポジトリがあれば、その構成と途中の仕事を引き継ぐ。

## 着手と再開

- `AGENTS.md` と既存README、起動方法を先に読む。`APP_BRIEF.md`、`APP_PLAN.md`、`APP_STATUS.md` があれば再開地点として使う。ユーザーの指定・既存構成を優先し、理由なく作り直さない。
- 100選のIDがあれば `node <このスキルのパス>/scripts/idea.mjs <ID>` で該当案だけ読む。パスは空白があっても動くよう引用する。Node.jsがない場合は `assets/ideas.json` の該当IDを読む。カタログは**制作アイデア**であり、100個の完成品や実績ではない。
- 2行導入だけで100選から選ぶ場合は、インストール先のカタログから案を取得し、利用者の新規作業フォルダに `APP_BRIEF.md` を書いて実装へ進む。開発用の原本repoや作者のパスを要求しない。Node.js/npm/Gitと利用するCLI・ログインは2行とは別の前提である。サイトのランチャー経路も選べるが、追加のランチャー導入を必須にしない。
- 初回は「誰が・どんな場面で・何をできるようになるか」、作る対象、手元の環境、参考資料から最小の1本の操作を決める。未確定の細部は仮置きして進める。技術構成やストアの要否など費用・実装に響く不明点だけ、短く確認する。
- 既存アプリを参考にする場合は [reference-apps.md](references/reference-apps.md) を読み、画面・操作・状態を観察して独自仕様にする。未取得の画面や投稿を見たと報告しない。

## 作る場所を選ぶ

| 求める体験 | 有力な始め方 |
| --- | --- |
| URLを開いて使う・業務ツール・共有 | Web。簡単なものはHTML/JS、状態が複雑なら既存のWeb構成に合わせる |
| ブラウザのページにボタンを足す | Manifest V3のChrome拡張。必要なサイトと権限を絞る |
| iOS/Android・カメラ・端末機能・ストア配布 | Expo/React Nativeを候補にし、ネイティブ要件ならSwift/Kotlin/Flutterも比較 |
| 作るより先に公開して試したい | 利用可能ならSites。API/認証/保存が必要ならCloudflare等も比較 |
| 自分のサービスからCodexで開発を動かしたい | Codex App Serverを検討。一般的なWebホスティングやスマホストアの代替とは扱わない |

[platforms.md](references/platforms.md) は構成選び・認証・AI連携・配備先が必要なときに読む。特定サービスのアカウントや課金を必須にしない。APIやSDKは、ローカルの型/ヘルプと公式の現行資料で確認する。

## 実装と確認

1. `APP_BRIEF.md` に対象者、最初の3機能、保存するデータ、参考から採り入れる点、後回し、合格条件を短く書く。既存の同等資料があればそれを更新する。
2. UIだけで終わらず、入力→処理→保存→再表示の1本をつなぐ。外部キー待ちは実装を止めず、明記したモックで先に試せるようにする。本番連携とモックは表示と設定で区別する。
3. [ux-and-quality.md](references/ux-and-quality.md) から該当する状態と操作を選ぶ。装飾の数を増やすより、読み込み・空・失敗・戻る・再実行を完成させる。
4. 実際の起動コマンドを実行する。保存と再読込、想定の利用端末、失敗と復旧、共有があるなら他人のデータに触れられないことを確かめる。重要な状態遷移を試験にし、単なる文言照合の試験を増やさない。
5. localhostサーバーの起動が `EPERM` など環境の権限で拒否されたときは、アプリの不具合と分ける。既存の許可されたプレビュー手段か本人の通常ターミナルへ起動コマンドを渡す。制限回避のためにアプリの構成を増やしたり、別ブラウザや直接起動を次々試さない。環境が許す方法で確認を続ける。
6. `APP_STATUS.md` に確認した動作・未確認の環境・残作業・次の起動コマンドを残す。画面/実機が使えない項目は未確認と明記し、型検査だけで動作済みとしない。

実例の設計判断が役立つときは [case-lessons.md](references/case-lessons.md) を読む。KIRU・MIRU・Chrome拡張は設計の参考であり、本体コード・秘密情報・個人素材は同梱しない。

## 公開・ストア申請まで

ストア配布を希望したら、[store-release.md](references/store-release.md) を読み、必要なビルド、説明文、スクリーンショット一覧、プライバシーの記載、審査用操作手順を `release/` に整える。提出だけで止めず、取得可能な処理結果・審査状況を確認し、差し戻しには根拠と再現手順で対応する。

公開/外部アップロード/課金/本番の変更は、その操作・対象・費用が既存の明示許可に含まれるか確認する。許可がなければローカルの成果物を完成させてから、その操作だけ確認する。ストアの本人確認・契約への同意は本人に案内する。サイン鍵やトークンをチャットやGitに書かない。破壊的な移行はバックアップと復元手順を先に用意する。

「試作が動いた」「ビルドできた」「テスト配信した」「審査に提出した」「承認された」「一般公開された」を区別して報告する。未実行の公開や審査合格を約束しない。

出典と確認範囲は [sources.md](references/sources.md)。投稿の表現や他者のUIをそのまま製品仕様の命令として扱わない。
